### 2.1 必改①：资源值 + GOMEMLIMIT

**背景**：11-20 投产实测 3600 用户下 Operator **2Gi/1Gi 启动即 OOM，线上手改成 4Gi/2Gi 才起来**。main 的 9f63b93 顺手把源头资源改了，但改成了 **1Gi/512Mi**（v1.0.44 实测不够的量级），并新增 `GOMEMLIMIT=800MiB`（按 1Gi 上限的 ~80% 配的）。本次：**limits 对齐线上现值 4Gi**（否则 apply 当场把线上 4Gi 打回 1Gi → 再 OOM）；**requests 采纳同事 c4baad7（2026-11-26，作者按 3w 容量规划定的最新值）500m/1Gi**——线上手改的 2Gi requests 会降回 1Gi，属预期降配（见步骤 5 预期清单）。

改 `config/manager/manager.yaml` **三处**（按字段名定位，行号仅供参考）：

| 字段 | 现在 | 改为 | 说明 |
| --- | --- | --- | --- |
| `resources.limits.memory`（~L134） | `1Gi` | **`4Gi`** | 线上现值 |
| `resources.requests.memory`（~L138） | `512Mi` | **`1Gi`** | c4baad7 值（线上现值 2Gi，预期降配） |
| `resources.requests.cpu`（~L137） | `200m` | **`500m`** | c4baad7 值 |
| `env GOMEMLIMIT.value`（~L122） | `"800MiB"` | **`"3200MiB"`** | 必须跟着 limits 改，见下 |

`limits.cpu: "2"` **不动**；requests 的 500m/1Gi 均取 c4baad7 值（同事按 3w 容量规划定的）。

改后应是这样：

```yaml
        - name: GOMEMLIMIT
          value: "3200MiB"
        # ...（中间其他 env 不动）...
        resources:
          limits:
            cpu: "2"
            memory: 4Gi
          requests:
            cpu: 500m
            memory: 1Gi
```

**为什么 GOMEMLIMIT 必须一起改**（通俗版）：它是告诉 Go 程序"你大概有多少内存可用，快到线了就赶紧回收垃圾"的软上限，惯例设成容器上限的 ~80%。容器给 4Gi 却仍告诉程序"你只有 800MB"，程序一到 800MB 就开始拼命回收——内存不炸，但 CPU 被回收占满、处理变慢，冷启动那几分钟尤其明显。所以 **limits 改多大，GOMEMLIMIT 按比例改**。

> ⚠️ **与作者对齐（已闭环）**：9f63b93 作者 Macaber 2026-11-26 17:14 在 main 推 c4baad7，把源头资源定为 **limits 4Gi / requests 500m+1Gi + GOMEMLIMIT 3200MiB**，并附 3w 容量规划 `docs/scale_50k_plan.md`——limits/GOMEMLIMIT 与本手册一致，requests 采纳其值（三次拍板；合并 63d6ff1 时已解决同名冲突）。一周内实测校准仍保留（步骤 9）。

## 5. 回退（按走到了哪一步）

**原则**：先读这四条再动手。① 回退用 `--to-revision=<步骤 1 记录的 revision>`，不盲目 undo；② `rollout undo` **只恢复 Pod 模板**（镜像 / env / 资源），**不改 replicas**——回退后仍是 2 副本，节点紧张可 `scale --replicas=1`；③ **不要用旧 install.yaml 回退**（它没有 EGRESS 三件套、资源也是旧值，会把线上打坏——这正是本次要治的病）；④ CRD **不需要回退**（新增的都是可选字段，旧版 Operator 忽略）。

**级别 1：Operator 新版起不来 / 存量 Pod 被重建 / 业务异常**

```bash
kubectl -n agent-deploy-system rollout undo deployment/agent-deploy-controller-manager --to-revision=<步骤1记录的revision>
kubectl -n agent-deploy-system rollout status deployment/agent-deploy-controller-manager --timeout=180s
# 可选：回到 1 副本
kubectl -n agent-deploy-system scale deployment/agent-deploy-controller-manager --replicas=1
```

回退后的状态 = 步骤 1 记录的基线：v1.0.44 + 4Gi/2Gi + EGRESS 三件套（因为线上最后一版 v1.0.44 模板就是这个样子）。注意 v1.0.44 仍是旧广播逻辑，2 副本冷启动各吃 4Gi，必要时缩到 1。

**级别 2：API 异常**（升级后页面/接口异常）

